# MarginFit 0.1.2 滚动 CPU 性能审查（2026-10-08）

## 结论

主要原因：智能内容宽度适配会显著提高 PDF.js 的真实显示倍率，而渲染开销随着画布像素面积增长。第二项：每个新页面的边界检测额外执行低清 PDF 渲染。第三项：重复的 wheel/scroll 监听与页面几何读取有小幅 CPU 开销。

本轮使用隔离 Windows Zotero 10.0.6、MarginFit 0.1.2、24 页奇偶不对称生成 PDF，不接触正式用户文献库。不更改产品源码。

## 真实倍率和负载

- 原生 page-width 数值倍率：1.17125。
- MarginFit 内容宽度数值倍率：2.2665094。
- 倍率比：约 1.935 倍；同一页面画布渲染像素面积理论上约 3.744 倍。
- L1 六页约 1.17 秒；新页检测约 0.12—0.32 秒/页（wall-clock，非纯 CPU 秒）。
- 打开阅读器至首次智能适配约 5.2 秒，其中含 Zotero 附件导入与初始布局。

## 开关、倍率分离对照

在缓存预热且滚动过程没有新检测任务的条件下，模拟 140 次滚动、每组约 4.3—4.8 秒，收集滚动回调和隔离 Zotero 进程树 CPU 秒。

| 模式 | 数值倍率 | 插件输入次数 | 输入累计耗时 | 新检测数 | CPU 约等效核心数 |
|---|---:|---:|---:|---:|---:|
| OFF + 原生倍率 | 1.17125 | 297 | 70 ms | 0 | 0.74 |
| ON + 相同原生倍率 | 1.17125 | 296 | 73 ms | 0 | 0.62 |
| OFF + 智能倍率 | 2.26651 | 297 | 63 ms | 0 | 1.34 |
| ON + 相同智能倍率 | 2.26651 | 297 | 86 ms | 0 | 1.48 |

> CPU 进程树采样每组只有 3—4 个点，且测试阶段之间可能残留 PDF.js 延迟重绘，数字只用作量级参考，不能作为精确性能承诺。1.0 个等效核心表示约一个逻辑 CPU 核心满负荷。后两组逆序重复的数据受布局延迟影响较大，不用于主要结论。

**控制变量的关键发现**：同一倍率下，仅改变 ON/OFF 没有一致的成倍 CPU 差异。即使 OFF，只要保留此前的高倍率，CPU 仍明显较高。切换 Detect Margins 到 OFF 本身不强制还原低倍率，因此用户若只关开关，未执行原生页宽，则 CPU 可能仍高。

## 源码中的 CPU 路径

1. 显示放大：MarginFit 根据窄版心计算较大的 PDF.js currentScaleValue，原生 PDF 画布、文字层和批注都必须按更高倍率重绘。这是滚动持续负载的首要因素。
2. 冗余渲染：src/runtime.js 的 detect() 无论是否有数字 PDF 文字框，都执行 page.getTextContent() + page.render() + getImageData() + rgba 克隆。L1 六页与 L2 邻页分别产生额外画布渲染，为了保护图表属于准确性取舍，但会竞争 CPU。
3. 事件双份：src/runtime.js 的 Controller.input() 同时由 wheel、scroll、pagechanging 等触发；每次还执行 page() 可见页及 DOM 几何计算、arm() 重建 500 ms 计时器。140 次合成滚动可产生约 296—297 次输入回调。
4. 初始化竞争：L1 建模通常在打开文档后启动，即使用户随后滚动，正在执行的六页分析仍可耗费 CPU。串行检测不等于前台 PDF.js 渲染空闲。
5. OFF 仍监听：切边关闭时 Controller 仍订阅滚动事件，并每 500 ms 进行全局阅读器发现轮询。可减少，但不足以解释高倍率条件下的几倍画布面积差异。

## 优化优先级

- P1：优先避免用户持续滚动期间启动下一页低清检测任务，让高优先级原生显示渲染先执行。已启动的渲染安全结束；保留 L1 必须先于 L2 的阶段关系。
- P1：研究重用已经绘制完成且覆盖完整页的 PDF canvas，减少额外 page.render()；如采用“文字框快速路径”，必须验证正文以外的图片、矢量图和脚注安全，不能简单放弃画面边界。
- P2：对输入事件去重/合并。wheel、touchmove 直接更新取消令牌和最后用户输入时间；主要页及边界框读取按动画帧或 50—100 ms 节流。OFF 状态跳过多余的页面几何检查。
- P2：自动定位前先比较实际 scrollLeft，未变化时避免多余赋值；此项对停稳抖动更有价值，而非滚动期间的主要 CPU 源头。
- 不建议单纯降低用户期望的内容适合倍率，或贸然降低渲染清晰度；两者会以牺牲阅读效果掩盖真正问题。

## 后续验证

- 30—60 秒实际触摸板/鼠标滚动，固定 PDF 倍率，在 ON、OFF 之间交替试验并统计帧时间、CPU 秒及 GPU。
- 冷启动、初次 L1、停稳 L2、完全缓存后纯滚动分别测，不混成一次总 CPU 数据。
- 覆盖至少一份上百页真实扫描 PDF，测每页额外渲染成本；比较缓存命中、低清画布复用、文本快速路径。
- 独立 Zotero 10.0.6 全进程树私有内存峰值本轮约 1.25 GB；包括 Zotero 自身 PDF/数据库/字体/多进程，**不能当作 MarginFit 单独内存占用**。
