# MarginFit 0.1.5 — 算法效率优化方案

制定日期：2026-10-09
状态：设计方案，未实施；以已正式发布的 0.1.4 为性能与正确性基线。
目标：减少插件额外 CPU、瞬时内存分配、GC 和缓存 I/O；保持原有可读性、智能裁边准确度和原生阅读行为。
项目：D:\OneDrive\AiPrograms\tools\zotero-margin-fit

## 一、现状与问题定位

当前调用链：Session L1 六页抽样 → L2 当前及邻页分析 → runtime.detect() → getTextContent() / textBox() →（有文字时）getOperatorList() / isTextOnlyOps() → 可靠纯文字且无批注时直接返回；否则 page.render() 低清画布 → getImageData() → cloneInto(RGBA) → inkBox() → 合并原始边界 → 缓存 → 缩放。
0.1.3 已将 wheel/scroll 输入的几何读取合并为约 75 ms；0.1.4 已实现严格纯文字快速路径、按 PDF 身份验证的磁盘边界缓存。本轮不重做这些已有效的设计。

已测微基准（Windows Node.js 合成数据，并非真实 Zotero 总 CPU）：
- textBox() 对 100 条文字执行 100 次：旧 16.25 ms，标量原型 3.87 ms，约 4.20 倍。
- 1,000 条文字执行 100 次：旧 136.01 ms，标量原型 30.4 ms，约 4.47 倍。
- 10,000 条文字执行 10 次：旧 81.51 ms，原型 7.81 ms，约 10.44 倍（此档更需重复确认，不能作为普遍收益）。
- inkBox() 的逐像素标量小改在典型正文/扫描页仅约 5%–10% 改善，空白页可能略退化；密集背景因提前退出改善明显。故不将像素循环微调列为首要任务。
- 用户真实观察：切边开启时 CPU 约 20%–25%，约为关闭时两倍；此值是体验基线，须与显示倍率差异、PDF.js 自身绘制成本分别测量，不能直接归因于检测算法。

本轮保持下列硬约束：
- 不改 PDF、批注、文本层、原生 Reset Zoom 以及 Fit Height / Detect Margins 界面规则。
- 不以降低清晰度、降低内容适配倍率、漏裁图表或强行删除页码换取性能。
- 保留固定四边 8 PDF 单位安全余量、L1 三组奇偶页先行、L2 固定邻页优先级、停稳 500 ms、滚动中冻结视图写入、L3 相对实际应用倍率 5% 死区。
- 纯文字快速路径必须保持逐页严格确认；文档级预测**绝不**直接产生可靠裁切框，也不得省略混合页的图像检测。
- 文档仅设计；此轮不修改 src、manifest、GitHub Release 或 updates.json。

## 二、实施分级及顺序

P0：建立可重复、分阶段的性能测量与正确性基线（先测再改）。
P1-A：将文字边界计算改为低分配标量算法（最明确的无损加速）。
P1-B：引入保守的文档级检测路径策略，避免明显不会成功的 operator-list 快速路径尝试。
P2-A：将持久缓存改为增量脏页记录与延后批量序列化/落盘。
P2-B：进一步减少停稳前后不必要的主要可见页几何查询和重复 async 验证。
探索项：只在独立分支研究渲染区域裁剪与已有 canvas 复用，**不进入 0.1.5 正式范围**。

## 三、P0 — 性能仪表与基准方法

在独立 Zotero profile 中增加只用于测试的性能计时，不添加用户可见的常驻统计。分别记录：
- PDF 获取、getTextContent、textBox、getOperatorList、getAnnotations、page.render、getImageData、cloneInto、inkBox 以及总 detect wall-time。
- 低清 render 次数、快速路径命中率、分类失败率、准确／预测边界数量、L1/L2 缓存命中、单页 RGBA 峰值字节。
- 持久缓存序列化次数、页面记录数、读写耗时、文件大小、每分钟 I/O 次数。
- 可见页几何读取频次、滚动中是否发生程序 zoom 或 scroll 赋值、原生 Zotero 主／内容／GPU 子进程的 CPU 秒与内存；帧率如可可靠采样才报告。

对照组必须同时包含：
1. 0.1.4、0.1.5 相同 PDF / 相同数值缩放倍率，Detect Margins ON/OFF；区分插件开销。
2. 真实智能内容适配倍率与原生适合页宽；区分倍率带来的原生渲染开销。
3. 冷缓存首次阅读与热缓存重新打开，不将两者混为一个平均值。
4. 纯文字、带大量矢量图的论文、扫描 PDF、含乐谱符号的 PDF、含高亮批注的 PDF、特殊背景与旋转页。
5. 典型 24 页验证件和至少 100 页的长文档；连续滚动、停稳翻页、反复打开分别测试。

基准至少三轮交叉顺序；先热身、避开首开初始化干扰，报告中位数和波动区间。不能只凭短时采样或一个 CPU 百分比宣布成功。所有复杂内容数据集保存测试来源与构造方式，禁止将 CPU 宏观变化冒充算法单项收益。

## 四、P1-A — 文字边界标量化（优先实施）

对应：src/core.js 的 textBox() / multiply()；tests/core.test.cjs、独立微基准。

目前每个 TextContent item 都创建：
- 四个点组成的临时 points 数组；
- 每个点的临时二维数组；
- 两组 points.map() 数组，再分别 Math.min(...)/Math.max(...)；
- 合并边界时的临时 bbox 数组。
对长篇 PDF，大量短文本元素会不断触发分配和垃圾回收。

计划将逐元素处理改为固定数量的局部标量：
1. 保留现有 PDF 变换矩阵乘法、长度和字体 ascent/descent 的含义；先计算四个角的标量坐标。
2. 使用 minX/maxX/minY/maxY 直接合并到累计边界；不构造 points、map 数组和临时 bbox。
3. 保留对缺失文本样式、旋转、负宽度、倾斜或退化变换的原有处理。
4. 仅在循环结束时创建最终 [left,top,right,bottom] 数组并 clamp；没有可用文字时继续返回 null。
5. 允许再比较“内联矩阵乘法”与保留 multiply() 的版本，但仅在额外微基准证明值得时采用；其他模块所使用的 multiply() API 不变。

严格验收：
- 固定样本：0°/90°/180°/270°、字体大小变化、斜体/旋转文字、带脚注与页码、单字、空文本、负基线方向。
- 随机生成合法仿射矩阵与含字体度量的 10,000 组样本，与 0.1.4 textBox() 逐项对照；坐标差必须在浮点噪声范围内（优先 1e-6 PDF 单位以内），不允许因优化漏掉任意有效边界。
- 真实 Zotero 端到端：相同页面 raw bbox、安全 bbox、缩放目标、阅读锚点及批注位置保持一致。
- 目标是降低 textBox 本身耗时和分配次数；此前合成数据约 4.2–4.5 倍只是待复现的参考，不作为系统 CPU 保证。
- 如在真实复杂文字下收益不明显，保持最简单、可维护的实现，不引入额外依赖。

附加低风险实验：isTextOnlyOps() 目前每页按 OPS 字典构建两个 Set；评估缓存已验证的 OPS→操作码集合（以 OPS 对象身份为键）是否值得。收益不足则不实施，避免让状态复杂化。

## 五、P1-B — 保守的文档级自适应检测路径

对应：src/core.js 的 Session、src/runtime.js 的 detect()，以及测试阶段 instrument；不改变逐页实际边界判断。

现状：当页面有 TextContent 时，通常先拉取 PDF.js operator list 判断是否能走纯文字快速路径；若存在矢量路径、图像或未知绘制指令，再进行低清渲染。在大量插图／乐谱类 PDF 中，分类可能经常失败而造成额外开销。

核心原则：**文档预测只选择先尝试哪条检测路径，绝不预测哪一页没有图形。**
- “text-probe”策略：保持 0.1.4 逐页严格 operator-list 白名单 + 批注判断；符合条件才免低清 render。
- “raster-first”策略：对明显混合/矢量型文档的后续部分页面不再额外请求 operator list，直接走现有 textBox + 低清 raster + union(text,raster) 路径。该路径不会丢掉矢量绘制或扫描信息。
- 空文字页面已有直接 raster 路径，不再重复分类，不增加文档推测复杂度。

启动规则：
1. L1 仍按三组奇偶共六页的固定抽样与真实检测完成，L2 不得先行。
2. 基于实际完成的 L1 样本统计 fastPath、raster、fallback、文本数量与绘图类型；样本不足、质量不可靠或高度混合时保持 0.1.4 现有 per-page 策略。
3. 若至少 5/6 个可靠抽样页含矢量/图像且严格纯文字分类均失败，才**候选**采用 raster-first；先以 A/B 基准证明跳过 operator-list 确实节省成本。阈值可以根据实测调整，不能凭经验直接定为最终常量。
4. raster-first 必须允许定期重新抽样，例如每 8 个未缓存新页进行一次完整快速路径检查；当后续页面表现转为纯文字或混合，应回到逐页探测。重新分类仍受 L2 调度与滚动暂停限制。
5. 用户主动 Fit Width/Height 时仍优先保证适配正确和响应速度；过时任务仍按 epoch/lifecycle 取消。
6. 已缓存的 raw bbox 始终直接命中，文档策略不会触发再次检测。首次重开若 L1 从旧磁盘缓存加载，缺失路径统计时保持 per-page 模式，不得把未知记录当作“图像页”；是否持久化少量分类元数据要另行评测收益并进行结构版本校验。

需比较的候选方案：
A. 原 0.1.4：所有有文字的未缓存页都尝试纯文字分类。
B. L1 类型判断后有条件选择 raster-first + 周期重探。
C. 仅在页面操作列表可廉价复用时分类（如果 PDF.js 已缓存的 operator list 对当前 reader 可可靠使用）。

必须按冷缓存“图表论文/乐谱”和“纯文字论文”分别计时：如 B/C 没有明确降低每页总 detect wall-time，或者会增加首屏等待、内存或维护难度，则不合入。任何分类不确定都默认保守处理，而不是将该页强制认定为纯文字。

## 六、P2-A — 缓存增量合并、批量写入与限额

对应：src/persistent-cache.js 的 Store、src/core.js 的 Session.read()/close()；tests/cache.test.cjs 和重开文档实测。

当前 schedule(cache) 在每次新检测后立即对整个内存 Map 调用 pack(cache)，构造完整快照；延迟 1,200 ms 才写盘。该“调度时全量序列化”在长文档逐页阅读时是 O(缓存条数) 的重复工作；flush() 又重新读取既有 JSON、合并并全量写回。

目标：把调度时开销减到近似 O(1)，将真正的批量合并放在 debounce 到期或关闭时执行。
1. Session.read() 记录“变更页号 + 已经验证的不可变 bbox 精简记录”，而不是交出整个 Map 立刻 pack；按页码去重，仅保留最后版本。
2. 同一文件、同一 PDF/算法版本，使用单一有序的写队列，避免并行打开多个阅读器互相覆盖；落盘前与文件中的合法现有记录合并。
3. 使用定时批量写入（先沿用 1.2 s；与阅读中 CPU 峰值对照后可以增大到 2–5 s），滚动活跃或正在绘制时优先延后非关键 I/O。关闭阅读器、插件禁用／卸载时尽量 flush，异常不阻断阅读器退出。
4. 考虑原子写入（临时文件+替换）以防崩溃造成半个 JSON；错误写入后下一次仍可从旧缓存或重新检测恢复，绝不应用损坏记录。
5. 缓存目录只包含 JSON 且允许删除。保留每文档最多 3,000 页的现有限额；若超过限额，再研究按最近使用页面替换，而不是默默永久拒绝所有新页。
6. 全局磁盘积累：先测实际每页记录的体积与用户资料库的预计规模。若有必要再实施空闲时的全局清理，例如按最近使用时间、最大总容量等限定；不得在滚动热路径扫描整个目录。
7. 如缓存结构或检测语义改变，显式提升 STORAGE_VERSION / VERSION；旧缓存可安全丢弃，绝不把未知字段当作可靠 bbox。

需增加单元/集成回归：
- 连续 100/1,000 页检测只触发少量批次，不逐页全量 pack。
- 两个独立 Reader 同时写同一 PDF，最终不丢页；重复打开命中原始的六页 L1 与 L2 精确页。
- 模拟磁盘写入失败、中途关闭、目录删除、JSON 截断与不同算法版本；这些情况回退重新检测，不影响 Zotero 打开文档。
- 保存超多页时缓存条数与磁盘大小受控；清理只能针对自己的 marginfit-boundaries 目录，绝不能清理其他 Zotero 数据。

## 七、P2-B — 去除不必要的静止几何读取

对应：src/runtime.js Controller.input()/page()/stable()/refine()、Plugin.discover()。

0.1.3 已将滚动中的 page() 调用从约 296 次降至约 46–52 次，因此不预计进一步优化仍有同量级收益。先做低风险测量：
- 分别统计 input() 的 75 ms 合并查询、stable() 重复调用 page()、refine() 缓存命中时的 page() 次数。
- 评估在滚动期间只更新时间戳与失效 epoch，等到真正停稳的 500 ms 时再查询一次主要可见页；页面改变可利用原生 pagechanging 事件发出轻量通知，但不能只依赖它。
- 当前页与 viewer 版本/旋转/viewport 均未变且短时间内没有滚动时，可复用单次可见页判定；缩放、布局、分屏、旋转、关闭标签或 resize 必须立即失效。
- 实际流畅度、自动适应时机和阅读锚点优先；如果额外节流导致换页识别迟滞、滚动停稳后误选页面，直接撤销。
- Plugin.discover() 的 500 ms 常驻轮询仅在测得非零实质开销后再考虑用事件辅助并降低频率，不能因为主观觉得轮询多而破坏新标签、分屏或独立窗口自动接管。

## 八、独立探索项（不在 0.1.5 实施）

A. PDF.js 现有页面画布复用：此前实际 probe 发现“渲染完成”页面也可能同时存在多个 canvas，直接取单个画布不保证完整；除非能证明完整拼接、旋转/深色主题一致和无丢失内容，否则不替换独立低清检测。
B. 像素处理在内容 realm 内完成：目的是省掉一次最长边约 800 px 的 RGBA cloneInto（现有临时位图约 1.92 MB）。需单独测跨隔离区调用、兼容和安全，且不能在读者显示线程形成更长阻塞。
C. 可视区域/内容区域裁剪 PDF.js 的原生高倍渲染：理论潜在收益更大，但需要处理多 canvas、文字层、批注与坐标变换，风险较高。作为独立分支实验，不能混入 0.1.5 稳定性能工作。

## 九、验收门槛、退化判断与执行流程

每项优化按“独立实现 → 纯函数测试 → 相同 PDF 的 A/B → 隔离 Zotero 集成 → 性能复核”推进。一个模块不过关就回退该模块，不拖累其他有效优化。

正确性硬门槛：
- 保留并通过现有单元测试至少 36 项、Zotero 阅读器 70 项、缓存与快速路径专项 13 项，并针对新算法补充测试。
- 全部用于裁边的 raw bbox 与 0.1.4 在等价检测路径下保持数值等价；保守通道无内容缺失。对于 textBox 标量化，目标误差 ≤1e-6 PDF 单位；实际内容不能被 bbox 排除。
- 图表、页码、细线、乐谱符号、脚注、批注、旋转、扫描浅灰文字，均不得因策略选择而被漏裁。无法确证时以原有保守检测为准。
- 不修改原生控件、不污染文献数据库、不影响 Zotero 自动更新、不引入新用户设置、不在持续滚动中程序化写入缩放/滚动位置。

性能验收：
- 各子阶段分别以真实测量的 CPU 秒、detect wall-time、写盘频率和 GC/分配指标决定是否保留；整体效果从“相同缩放倍率、同批 PDF、同一机器”测出。
- P1-A 必须提供重复微基准及至少一组真实长文档检测测量；P1-B 若导致扫描/带图论文冷缓存检测反而更慢，必须保持关闭/回退。
- 0.1.5 的目标是使典型工作负载 CPU 不劣于 0.1.4，并使至少一种典型文字/混合文档的检测阶段总耗时有可复现的实质下降。对渲染主导的工作负载不承诺整体 CPU 固定降幅。
- 对体验层面的 20%–25% CPU 用户基线须原样记录，然后在相同 PDF 与倍率条件下复测；不能把文字计算 4 倍微基准直接当成整机 CPU 下降 75%。

阶段顺序：
1. P0 先固定基线与指标。
2. P1-A 单独改 textBox 并跑回归。
3. P1-B 做候选策略 A/B；数据证明有效才合入。
4. P2-A 增量缓存与故障恢复，测 I/O；确认收益。
5. P2-B 只在前述优化仍有明确几何热点时执行。
6. 完整安全审查、记录收益与未解决问题，构建本地 0.1.5 XPI。
7. **仅经单独发布决策后**推送 v0.1.5 GitHub Release、再更新 updates.json，并实际下载校验和执行 Zotero 原生升级测试；不能先改更新源。

交付产物：实施变更、扩展后的单元/集成/性能测试、同倍率 A/B 结果表、风险回归记录，以及下一阶段交接文件。失败实验也保留说明，便于未来决定。
