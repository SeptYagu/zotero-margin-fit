# MarginFit 0.1.6 — 稳健边界支持度与横纵分离适配方案

日期：2026-10-09
状态：设计方案；尚未实施、测试或发布
基线：已正式发布并在 Zotero 10.0.6 验收的 v0.1.5
核心方向：Robust Boundary Detection / Axis-Specific Fitting
用户原始案例：音乐理论书第 76 页（正文、例 4.14/4.15、左下角页码 76、底部 Chapter 4）

## 一、问题定义与设计原则

### 1.1 观察与问题

用户展示的页面，主体段落和乐谱示例的左边缘明显比孤立的左下角页码 76 更靠右。Chapter 4 位于页面底部。现在如果页码被纳入 x_min，插件会使用过宽的内容矩形计算“适合宽度”，使正文未能充分放大；即便章名决定下边界，也不应要求它一定决定横向适配宽度。

该页面的截图可用于建立视觉验收目标，但截图不能证明 PDF 内部是扫描、矢量、纯文字还是混合 PDF，也不能直接证实插件目前返回的 raw 坐标。实际定位需要取得原 PDF 该页，或在独立测试 profile 中输出检测记录；**不得把截图上的估计像素坐标直接当作 PDF 真实数据**。

### 1.2 数学澄清

当前算法求所有内容的轴对齐包围矩形 [L,T,R,B]。矩形的对边天然等长，不会由于一个页码变成真正的梯形。用户提出的“梯形不可接受”应转化为一个可测试条件：沿页面高度观察左右墨迹边界轮廓时，如果仅极少量边缘行/孤立内容远离主体边界，应将其视为“局部突出候选”，而不是直接由它决定全页面横向拟合宽度。

核心不是“强制四边相等”，而是“对主体边界施加跨行稳定性支持；对罕见局部凸出进行严格审查”。

### 1.3 两个互补的功能目标

A. **横纵适配解耦**（用户这页的直接需求）：
- Width Fit：以主体左右边界为首要依据，可忽略经核实的孤立页码对 L/R 的影响。
- Height Fit：先沿用保守的完整 T/B，允许 Chapter 4、页码继续决定底部边界。
- 任一轴都不直接修改 PDF、文字层、批注、页面画布与底层原始内容。排除某项影响适配不等于删除该项内容；该项可能被放大后的视窗遮住，但仍可使用原生缩放/滚动查看。

B. **更通用的稳健边界**：
- 在扫描页、混合 PDF、乐谱图例等 0.1.5 页码语义识别无法覆盖的页面上，利用既有墨迹检测，找出正文/图形“广泛支持的外缘”。
- 只有经多重证据表明是孤立的边缘附属物，才允许不参与某一轴的缩放；不能仅凭“少数像素在外面”就排除图、谱、脚注、公式、细线。
- 不确定则恢复完整原始边界，内容保护高于裁边紧凑程度。

## 二、0.1.5 实际代码基线与根因

- src/core.js: inkBox() 每页在最长边约 800 px 的低清 RGBA 画布上逐像素扫描，对所有可识别墨迹求 left/right/top/bottom 极值；孤立页码、细线也会参与计算。
- src/runtime.js: detect() 在混合页上取 union(textBox, inkBox) 作为 raw；只对严格纯文字且无批注的页面有 textAndFolio()/folioPattern() 快速路径。
- src/core.js: scaleDecision() 当前既用于 Width Fit 又用于 Height Fit，读取同一个 record.raw；fitPageRecord() 只能在符合纯文字高置信页码条件下更换整个 raw。
- parityModels() 以 L1 六页（含奇偶）原始框取包络；如果样本带孤立突出，可能污染对未分析页面的预测。
- 现有安全机制：8 PDF 单位边缘留白、L1 先行、L2 当前/邻页、滚动中不写入缩放或位置、停稳 500 ms、5% 死区、可逆 hook、磁盘缓存和文件/算法版本校验。全部保留。

不直接修改 inkBox() 返回的完整极值框，也不粗暴裁掉最后 10% 的整条页脚带；应在完整 raw 之外计算单独的稳健拟合边界。

## 三、新的数据表示：完整边界与分轴拟合边界

建议每页保留下列语义（名称仅为方案，最终实现可按代码风格调整）：

- originalBounds = [L0,T0,R0,B0]：完整文本/墨迹外接框，含页码、页脚、谱例、细线；与 v0.1.5 保守路径数值等价，供回退、审查。
- candidateEdges：边缘分析的摘要：按行的最左/最右墨迹坐标、有效行支持度、密度或距离阈值信息；可临时保存在内存，只持久存通过审查的紧凑坐标和状态，不持久化整页 RGB 或正文内容。
- widthFitBounds：用于 Width Fit 的 [Lw,Tw,Rw,Bw]。主要允许改变 L/R，默认 T/B 仍沿用 originalBounds；宽度计算只取 Rw-Lw，安全边距继续应用。
- heightFitBounds：用于 Height Fit 的 [Lh,Th,Rh,Bh]。第一阶段完整等于 originalBounds，以免孤立页码和 Chapter 4 从纵向可视区域意外消失；未来是否排除运行页眉/页脚单独验收。
- decisionEvidence：标识局部突出区域、支持度、为何确认/为何拒绝、来源（text/raster/mixed）、算法版本、置信状态。

选择拟合框时传入 width/height 方向，不以替换一个全局 raw 的办法同时改变两个方向。原页面真实 bbox 和全部 UI 内容始终保留。

**重要：**“横向不受页码影响”和“纵向仍包含页码/章名”不是矛盾；可为两个拟合模式计算不同边界，但绝不能制造不对应实际页面内容的坐标转换。窗口居中、阅读锚点、原生 PDF.js 缩放坐标仍需严格校验。

## 四、边界支持度算法（替代孤立像素决定横向极值）

### 4.1 第一步：在现有逐像素扫描中积累行边界

在 inkBox() 的一次 RGBA 扫描中，同时维护以下低维统计：
- 每个有效扫描行 y 的 left[y]、right[y]，有效墨迹像素量 inkCount[y]；允许以小的垂直分桶（例如 2～4 低清像素）减少噪声。
- 页面总体的完整墨迹极值 originalInkBounds 继续照旧计算。
- 可选：每行少量墨迹 run（连续段）的起止位置、边缘候选区域墨迹面积；只有需要确认时才使用。这是解决页码与真正图形恰好处于同一行的后备手段。

性能约束：保持现有 **一次低清 PDF render、一次整页 RGBA 遍历**。新增统计最多 O(H) 的行数组和少量 ROI 信息。不能为了稳健边界再运行一次整页 render 或构造尺寸为 W×H 的第二张完整像素图。

### 4.2 第二步：估计稳定的主体外缘

从“具有连续正文/图形支持”的行或垂直分桶，建立左右边界分布：
- 先找出较长垂直范围中频繁出现的左起始位置和右覆盖范围，允许段落行长度不同；左右要分别估计，不能假设正文是水平对称的。
- 评估候选边界是否被足够多**空间上分散**的行支持，避免同一个大字或短装饰区域伪装成多行正文。
- 使用稳健分位数、加权直方图的稳定峰、垂直连续性等候选算法进行 A/B；不能一开始硬编码全书统一的“去掉最外侧 5% 行”。
- 页眉、页脚和正文可能有不同水平对齐模式；跨页奇偶版心也可能左右交替。只在同一页旋转/坐标体系下处理，跨页模式按奇偶分别建模。
- 非连续正文（两栏论文、图文混排、乐谱系统分组）不得因缺少单一稳定峰而被裁掉；若主体模型分裂/证据冲突，回退 originalBounds。

建议初步复杂度：现有像素扫描 O(W×H)，附加 O(H+B) 的行统计/小直方图 B；高分位与排序如需 O(H log H) 应另测开销，并优先考虑固定大小桶或线性选择。

### 4.3 第三步：判定孤立“突出候选”而非直接剔除

对 originalBounds 与稳定主体 L/R 的差值形成 protrusions：
- 左突出示例：左下角页码 76 导致 L0 远小于 Lbody，但支持它的墨迹只占底部很小高度，远离正文左缘。
- 候选必须与主体具有显著水平距离，位于低风险边缘（通常页首/页尾），墨迹量小，且与主体/图形之间存在可验证的空间隔离。
- 候选附近如存在真正的延伸谱线、图框、注释箭头、文本脚注、长图例、横向表格或其它连接，**拒绝排除**。
- 对 raster 页只凭行轮廓可产生候选，无法证明是页码时，应结合限定范围 ROI 的 run / 连通性分析和 L1 已知页码/页脚位置规律。不得仅凭形状“像数字”就作页码语义判断，也不调用 OCR。
- 对电子文字页复用 getTextContent() 已算出的文字框与 v0.1.5 folio 信息；可验证该孤立区域是否对应页码或短运行页脚。对混合页必须同时核实位图中同一区域是否包含其它墨迹，否则仍被 union(text,raster) 冲回完整框。
- 多个候选区域或置信不足时，允许完全不排除；**误排正文代价高于未排页码**。

注意：算法不要求页码必须在左下、右下或页面中央，也不要求一定识别出阿拉伯数字。它依靠“跨行支持度 + 边缘隔离 + 可用的跨页证据”，把语义识别作为可选加分项。

### 4.4 第四步：分轴产出与几何约束

对通过审查的候选，只调整它所影响的适配轴：
- 左下角页码 76：可调整 Lw，Bw 保留原值；若只是页码单独决定最左界，应提升 Width Fit 放大倍率。
- 底部 Chapter 4：第一阶段保持 Bh 为原值，不追求删除底部章名；如果章名本身也延伸出正文左右边界，必须单独判定能否排除其横向影响，不能默认忽略。
- 其它安全内容均应位于新横向边界内部；只允许确认的边缘附属区域位于拟合框之外。设最大边界收缩限制及确认前后记录，阈值须由测试校准。
- originalBounds 始终保留完整墨迹框；用于预测失败回退或用户恢复原生视图。
- 现有 safeBox() 的 8 PDF 单位 padding 对新的拟合框仍只应用一次；缩放上限、5% 死区和滚动锚点保持不变。

### 4.5 L1 奇偶抽样、预读与预测

- 保持 L1 现有 6 页顺序，L2 当前页/邻页顺序不变；不能为了判定边缘而每翻页额外扫描全书。
- 从已有 L1 的按页摘要估计奇偶页主体边界和常见边缘附属物区位，预测时沿用“证据不足即完整框”。
- 未精确检测的新页面，不可把之前某页的页码遮罩、正文框无条件照搬。预测 width-fit 仅在跨样本布局一致、无危险超出时启用；否则保守。
- 滚动中不触发新的 PDF render 或 fit 写入；稳定 500ms 后按既有流程精确检测并择机应用。

## 五、性能预算、缓存与兼容性

### 5.1 性能控制

- 不增加 PDF.js 原生渲染次数；有纹理/混合内容页继续复用现有 800px 级低清 render 结果。
- 不重复整页遍历 RGBA；新增行最左/最右/数量等信息应在当前 inkBox() 循环内累积，避免跨隔离域新增整张图片复制。
- 电子纯文字页复用 textBox() 既有遍历和 folioCandidates，不为“边界支持度”强制调用 raster 或 OCR。
- 在原有检测方法输出完整 raw 之后，只处理 O(H) 行概要，必要时局部 ROI；不在输入事件、滚动热路径做支持度重算。
- 稳健模型单页计算一次，结果连同版本和置信度按 v0.1.5 已有策略缓存。热缓存打开不得重新运行 pixel/row analysis。
- **必须区分插件分析 CPU 与 Zotero 渲染 CPU**：更紧的横向拟合通常导致放大倍率升高，PDF.js 主画布像素可能增加，整机 CPU、GPU 或内存反而上升。这是可视尺寸收益和渲染成本的权衡，不能宣称稳健边界算法本身能降低用户看到的总 CPU 百分比。
- 对统计计算单独 A/B：同倍率比较 v0.1.5 与 v0.1.6 detect wall-time、扫描像素次数、RGBA bytes、分配/GC、缓存命中、渲染次数。然后另测“实际智能缩放后”的整机 CPU，明确列出倍率差异。

### 5.2 缓存和升级

- 新增 widthFitBounds/heightFitBounds 或其它候选元数据时，提升 src/core.js VERSION 和 src/persistent-cache.js STORAGE_VERSION，旧版条目不得无校验当成“已稳健裁边”。
- 缓存仍保留合法的完整 originalBounds 和原 PDF 身份（PDF.js fingerprints、页数、文件大小/修改时间、旋转/算法版本）。仅存经过验证的数值型拟合框和证据摘要，不存整页文字、位图、OCR 或用户阅读历史。
- 缓存损坏、样本不足、旋转变化、文件更换、异步检测过期、分屏不同 viewport，全部必须安全回退，而不是沿用上一页的边缘排除结果。
- 不调整现有 3,000 页上限、合并写入机制和已验证的释放/卸载生命周期，除非独立测试证明必要。

## 六、验收样本矩阵与可观测指标

### 6.1 目标案例

**A01 — 用户截图中音乐理论书第 76 页**
- 内容：顶部正文解释、两个乐谱/节奏示例 4.14 与 4.15、左下角孤立 76、底部 Chapter 4。
- 期待：在确认独立页码和正文版心后，Width Fit 的主体左界不再受 76 左突出的单独影响；正文/谱例的右界保持完整。
- Height Fit：仍可保留 Chapter 4 和页码导致的纵向下边界；不因横向优化强行删除页脚。
- 真实 PDF 若无法获取：根据截图制作形状等价的合成 fixture **只能验证思路**；不能把它当成用户原 PDF 已实际修复或宣称 100% 重现。

**A02 — 同类页的页码在右下角、左/右奇偶交替**
- 要求两侧分别识别，不能默认左下脚，保留奇偶版心差异。

**A03 — 纯文字页码已由 0.1.5 folioPattern 确认**
- 0.1.6 至少维持 0.1.5 的识别范围和边界结果；避免新策略回退后把已能排除的数字又加回来。

### 6.2 必须拒绝错误剔除的反例

- B01：整页只有少量文字的标题、目录、扉页、两行短诗/短谱。
- B02：宽乐谱、五线谱末端/谱号、延伸连线、独立表情与小节编号、乐谱左侧括号。
- B03：超出正文宽度的完整图表、表格、横向公式编号、示意箭头、插图题注。
- B04：窄栏+宽图、左右双栏不对称布局、正文中途缩进、引文/脚注版式不同。
- B05：底部很长的真正脚注、文献编号、版权行、编辑附注；单独的数字未必是页码。
- B06：扫描倾斜、边缘污点、反色背景、低对比度、小字、透印、文字与页码连成一笔。
- B07：旋转 90/180/270 度、页面裁剪盒有偏移、双页拼版、横向页面、不同页面大小。
- B08：已有高亮/批注越过正文左缘；坐标不得改变，显示不得因拟合/滚动位移发生错误。
- B09：底部 Chapter 4 虽与页码同一行，但位置接近主体左界；只排除页码横向影响，保留章名文字。
- B10：章节首页没有页码、页码变化/重启、前言罗马数字、跨页无稳定规律。

### 6.3 测试指标和判定

每个 fixture 需有经人工标注的正文、谱例、图表、脚注、页脚和页码 bounding polygons/boxes（扫描的真值允许一定误差），记录：
- originalBounds、widthFitBounds、heightFitBounds，以及变化的是左/右/上/下哪一个方向。
- 哪些组件贡献了被剔除的局部突出；置信依据：行支持、连通/ROI、跨页、文字证据；没剔除的原因也要记录。
- 目标 Width Fit / Height Fit 实际 PDF.js currentScale、正文可视范围、实际锚点、原生 Ctrl+0、Reset Zoom 和横向滚动。
- 误排重要内容计数、页码成功排除率、不同文档类型 fallback 比率、误排风险类别。
- render 调用次数与参数、RGBA 次数、单页 detect 耗时、CPU/内存、冷/热缓存表现；高倍率主渲染单独计。

硬性通过条件：
1. A01 形状等价样本中，左突出页码可被排除出 Width Fit，底部 Chapter 4 可继续参与 Height Fit，谱例及正文所有重要内容完整保留；真实源 PDF 取得后复验。
2. B01–B10 的已标注重要内容不得被剔除；若无法判断则保持 v0.1.5 的 originalBounds。
3. v0.1.5 的 47 项单元、70 项 Zotero 阅读器集成、18 项页码/缓存专项全部通过，并为稳健边界新增正例与阴性测试。
4. 维持“完整原始边界 + 独立 Width/Height 适配框”语义；不得把原始框替换掉，或让 Width Fit 的选择意外缩小 Height Fit。
5. 相同 PDF、相同原生倍率、冷缓存下，新算法**零额外 PDF render**，像素扫描仍然只有一次；额外 CPU/分配需要有可靠测量并保持合理，不可用大幅性能退化换取裁边效果。
6. 在 Zotero 10.0.6 的独立 profile 进行真实用户路径测试；不修改正式 Zotero 文献库、PDF、批注及已发布 0.1.5。

## 七、分阶段实施步骤与交付要求

**S0 — 冻结基线与问题重现**
- 记录 v0.1.5 的真实 width/height 检测数据和 Fit Scale；确认现有 L1 / L2 哪一阶段产生了过宽的 L，是否确实由页码而非隐藏图形、异常 PDF bbox 或 Chapter 4 横向位置引起。
- 如用户实际 PDF 不可用，先建立与截图布局对应的合成 PDF，并清楚标记它不是原始问题文件。
- 固定原始完整框的真值、显示倍率与测试脚本，保留截图案例及预期。
- 输出：S0 baseline/diagnosis 文档及 fixture，单独 Git commit + push。

**S1 — 零额外渲染的边缘统计原型**
- 在既有 inkBox() 像素循环累计 left[y]/right[y]/inkCount[y]，保持 v0.1.5 原始边界算法不变。
- 先输出只读统计和可视诊断（不用它自动裁边），评估电子、矢量、扫描和乐谱样本的支持度分布。
- 用纯函数微基准测新增统计与原算法 O(W×H) 的时间、内存、GC 成本，负收益方案及时撤销。
- 输出：统计实现、单元与性能结果，独立 commit + push。

**S2 — 主体边界与突出候选的稳健分类**
- 比较不同策略：分桶支持度、稳健分位数、按行有效面积加权、局部 ROI 连通性；禁止只有一种百分位阈值的激进裁切。
- 正例 A01/A02 和反例 B01–B10 同时测试；任何可能漏掉乐谱或图表的启发式都不能直接投入 Width Fit。
- 分类结果只作为 candidate，不覆盖原始 bbox；候选证据不足、布局分裂或接触重要内容时拒绝。
- 输出：候选分类器、真值表与失败案例，独立 commit + push。

**S3 — 横纵分离与实际 Fit 验收**
- 为 Width Fit / Height Fit 明确传入适配框；初期 Height Fit 继续使用完整原始框。
- 电子纯文字路径复用现有 0.1.5 folio 与 textBox，混合/扫描仅在保守条件满足时允许忽略孤立突出。
- 检查 L1 奇偶预测、L2 精确测量、翻页稳定倍率、停稳与主动 Fit、文本层/批注层坐标。
- 在独立 Zotero 中验证页码导致的左过宽实际消失，并验证下方 Chapter 4 没被误裁；不以只显示“候选识别成功”代替真实缩放效果。
- 输出：Zotero 集成记录、截图/坐标对照，独立 commit + push。

**S4 — 缓存升级和性能 A/B**
- 升级缓存与算法版本，持久化最小数值字段；旧缓存完全可安全回退。
- 同条件对照 0.1.5/0.1.6 的冷/热分析 CPU、内存、画布 render、原生与智能倍率；真实用户缩放下的 CPU 与插件识别 CPU 分开呈现。
- 如混合/扫描路线过于慢或存在漏内容风险，仅保留已验证的文本或特定几何条件；不能因个别页面成功就默认对所有 PDF 启用。
- 输出：性能表、回归、缓存兼容性报告，独立 commit + push。

**S5 — 全面验收与发布决策**
- 运行全部原有测试、新增阳性/阴性测试、隔离 Zotero 功能回归、PDF 字节不变校验。
- 汇总已解决的页面类别、明确暂不支持的复杂情况与风险；构建本地 0.1.6 XPI。
- **此方案阶段不提前发布、不修改 updates.json。** 经独立发布决定后，按“GitHub Release 上传 XPI → 公开下载 SHA-256 复核 → 更新更新源 → Zotero 原生升级测试”的既有路径执行。

执行规则：如后续获准连续实施，每阶段完成后必须记录结果、提交并推送、重新读取本方案及最新交接文档，再继续下一阶段；测试不达标的子策略保留失败记录并回退，不能绕开正确性门槛。

## 八、明确不在 0.1.6 范围内的事项

- 修改 PDF 文件的 MediaBox/CropBox、删除页码/章名/批注、OCR 全文、机器学习模型训练。
- 额外的整页低清渲染、替代 Zotero/PDF.js 原生页面画布和文本层的自制阅读器。
- 无依据地屏蔽整行页脚或所有孤立对象；扫描件不能直接套用 0.1.5 的纯文字连续编号规则。
- 自行改变完整 PDF 的纵向 Fit Height 以追求版心更大——该方向须单独评估页脚/页眉的重要性与阅读目标。
- 在尚未验收该边界模型之前，向用户承诺整个 Zotero CPU 必然下降。

## 九、决策摘要

本次采用**“保留完整墨迹框 → 同次扫描提取跨行边界支持度 → 识别孤立突出 → 只在高置信下修正某一方向的适配框”**的路线。

用户所说的“对边等长、不能像梯形突出”，在实现上对应“主体左右边界有足够纵向支持，孤立的页码不能独自决定全页宽度”，而不是改变矩形本身的几何性质。

优先解决截图第 76 页的横向边界，纵向继续完整保留 Chapter 4；同时以乐谱/脚注/宽图表为重要反例，确保不以漏掉内容换取倍率。该设计有望在基本不增加额外渲染成本的前提下提高 Width Fit 的可用性，但识别增量 CPU 与放大后原生渲染 CPU 仍须分别实测。
